# CSV Output

What each extraction writes, which tables make it in, and what happens to rows
the OCR got wrong.

## Files

| File | Contents |
| --- | --- |
| `storage/output/<doc>.csv` | every qualifying table merged into one product table |
| `storage/output/<doc>-rejected.csv` | rows that could not be trusted, each with a reason. Written only if there are any |
| `storage/output/<doc>/individual/table-N.csv` | every table exactly as read, qualifying or not |

The individual files exist because the merge is opinionated — it drops banner
rows and skips tables without the required columns — and that judgement has to
stay checkable against the raw output.

Two columns are added to the merged CSV:

| Column | Meaning |
| --- | --- |
| `source_table` | which table on which page the row came from |
| `repaired` | `True` if the row was realigned (see [Row repair](#row-repair)) |

## What qualifies

A table joins the merge only if, after header canonicalisation, it has **both**
`Midas Code` and `Consumer Deal`. That gate is what keeps banner tables,
contents pages, and page furniture out of the product data.

Anything skipped is reported: the response and the UI both show
`tables_merged / tables_extracted`, and the skipped tables remain readable
under `individual/`.

### Header canonicalisation

Headers are mapped onto canonical names before the gate is applied, because
the OCR is inconsistent about case, spacing, and abbreviation.

| Seen in the wild | Becomes |
| --- | --- |
| `MIDAS CODE`, `MidasCode`, `midas code` | `Midas Code` |
| `CASE SIZE`, `PACK SIZE`, `pack size` | `Case Size` |
| `POR`, `POR%`, `Prom POR`, `Promo POR` | `Promo POR` |
| `Barcode`, `EANBarcode` | `EAN Barcode` |

An unmapped spelling silently becomes its own column, which is how a real
column ends up forked in two — `Prom Por` sitting beside `Promo POR`. Every
header that falls through to the Title-Case fallback is therefore **logged**,
so new variants surface instead of quietly fragmenting the data.

## Rows the merge changes or removes

Nothing is dropped silently. Every row is accounted for in the response
counts.

| Case | What happens |
| --- | --- |
| Blank `Midas Code` | a section-header row — dropped, counted as `blank_midas` |
| Every cell identical | a category banner (`FRESH`, `GROCERY`) — dropped, counted as `banners` |
| `Midas Code` misaligned | **repaired if the repair can be verified**, flagged `repaired` |
| Anything else | written to `<doc>-rejected.csv` with the reason |

A category banner is one full-width merged cell, which `pd.read_html`
replicates into every column of the row — which is exactly how it is detected.

## Row repair

OCR sometimes shifts a row sideways by a column, leaving a case size where the
Midas code should be:

```text
correct : Product Description='AERO GIANT ORANGE'  Case Size='15 x 90G'  Midas Code='M304079'
shifted : Product Description=<blank>  Case Size='AERO GIANT MILK'  Midas Code='15 x 90G'  EAN='M304095'
```

Repair anchors on the cell that actually looks like a Midas code (`^M\d+$`),
then generates candidate realignments and picks one **only if it is verifiably
better**.

1. If every non-empty cell is identical → banner row, dropped.
2. If there is no `M…` value, or more than one, the row is rejected — there is
   nothing to anchor on, or the alignment is ambiguous.
3. Otherwise, candidates are generated by deleting the spurious cells at each
   possible position before the anchor (and by padding, when the row is short).
4. Each candidate is scored against per-column value shapes: `+1` for a value
   that fits its column, `−1` for one that does not.
5. The best candidate is accepted **only if it scores strictly higher** than the
   original row. Otherwise the row goes to the reject file untouched.

| Column | Expected shape |
| --- | --- |
| `Midas Code` | `^M\d+$` |
| `Case Size` | `N x N … G/ML/KG/L` |
| `Prom WSP`, `Std RSP` | currency |
| `Promo POR` | percentage |
| `EAN Barcode` | digits |
| `Image`, `Shelf` | empty or a small integer |

`Consumer Deal` deliberately has no validator — it ranges from `£6.00` to
`HALF PRICE: £3.27` to `ANY 2 FOR £3.00` and would only add noise.

### Why verification is not optional

The obvious implementation — anchor on the code and shift the whole row — is
wrong. It repairs one real document and corrupts another:

```text
before : Product Description='CARLSBERG PILSNER PM525'  Case Size='[F87]'  Midas Code='6 x 4 x 440ML'
naive  : Image='CARLSBERG PILSNER PM525'  Product Description='[F87]'  Midas Code='M302447'   ← wrong
```

Here the displacement starts mid-row: a spurious `[F87]` cell was inserted, so
`Product Description` was already correct. Shifting everything fixes the Midas
code by pushing the product name out of its column. Scoring rejects that
candidate in favour of the one that deletes `[F87]` alone.

Scores frequently tie, because the column that separates the candidates
(`Product Description`) is free text with no shape to check. Ties break toward
**discarding the least information** — an empty cell over a filled one, a short
token like `[F87]` over a product name. That single rule is what makes both
documents come out right.

### Repair runs per table, before the merge

Realignment is positional, and concatenating tables unions their columns into
an order that belongs to no single table. Repairing after the concat produced
rows with a percentage in `EAN Barcode`. `clean_rows()` therefore runs on each
table while its own column order is still intact, and `merge()` concatenates
the results.

## Checking the merge without re-running OCR

`scripts/replay_merge.py` re-runs the whole merge over OCR JSON already on
disk. It takes about a second and needs no GPU, which makes it the right way
to iterate on the normaliser.

```bash
python scripts/replay_merge.py            # every document
python scripts/replay_merge.py "BUD*"     # one of them
```

```text
BUD NP10 Trading Pack (1)
  tables       : 41 qualified of 55 found
  rows in      : 706
  rows out     : 689  (repaired 3)
  dropped      : 3 blank Midas, 17 banners
  rejected     : 0
```

## Verified results

Measured on real documents, replayed from stored OCR output produced with
`layout_nms=True`:

| Document | Pages | Tables | Qualified | Rows | Repaired | Rejected |
| --- | --- | --- | --- | --- | --- | --- |
| BUD NP10 Trading Pack | 68 | 55 | 41 | 689 | 3 | 0 |
| test1.pdf | 5 | 6 | 4 | 72 | 4 | 0 |
| test2.pdf | 5 | 6 | 4 | 65 | 0 | 0 |

Since `layout_nms=False` landed (see [the gap below](#known-gap-closed)),
test2.pdf re-run end to end through `POST /api/extract` on an A16 gives:

| Document | Pages | Tables | Qualified | Rows | Repaired | Rejected |
| --- | --- | --- | --- | --- | --- | --- |
| test2.pdf | 5 | 5 | 5 | 84 | 0 | 0 |

BUD NP10 and test1.pdf have **not** been re-run under the new setting.

Merged cells survive: `Consumer Deal` is a vertically merged cell spanning
several product rows, and the 689-row BUD output has **zero** blank
`Consumer Deal` values — `pd.read_html` replicates a `rowspan` into every row
it covers.

## Known gap (closed)

**A wide table split vertically by OCR used to lose its rows.** On page 5 of
one document, PaddleOCR detected a single product table as two side-by-side
blocks:

```text
table 5:  x 1097→1848   Product Description, Midas Code, EAN Barcode
table 6:  x 1837→2286   Prom WSP, Std RSP, Consumer Deal, Promo POR
```

Same rows, different halves, same vertical span. Neither half had both required
columns, so both were skipped and roughly 19 products never reached the CSV.
They were not joined automatically because the halves reported **different row
counts** (19 vs 24): a positional join would silently pair prices with the
wrong products, which is worse than the omission.

**`layout_nms=False` in `engine/paddle_engine.py` fixed it at the source**, so
no join was ever needed. Disabling non-maximum suppression makes the layout
model keep the whole-table region instead of two overlapping candidates.
Re-running test2.pdf end to end confirms it:

| | `layout_nms=True` | `layout_nms=False` |
| --- | --- | --- |
| Page 5 tables | 2 (19 rows × 4 cols, 24 rows × 4 cols) | 1 (19 rows × 8 cols) |
| Tables detected | 6 | 5 |
| Tables qualifying | 4 | 5 |
| Rows in merged CSV | 65 | 84 |

The 19 recovered rows carry no blank `Midas Code` or `Consumer Deal`, and the
pairing is right rather than merely present: every `PM219` product line has a
£2.19 `Std RSP` and every `PM229` line a £2.29 — the price-marked pack size in
the product name matches its own price, which a positional join across
mismatched halves could not have produced.

The setting is still marked experimental in its own comment and has not been
validated across other documents. BUD NP10 and test1.pdf should be re-run
before it is trusted generally — disabling NMS can also let genuinely
overlapping regions through as duplicate tables.
